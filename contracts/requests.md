# 请求、结果与协调语义

关联：OPS-01…08、CON-04…08。状态：语义设计草案；字段名、枚举和退出码表尚未定版。

## 四层事实

| 层 | 可回答的问题 | 不能据此推断 |
| --- | --- | --- |
| 本地 CLI/IPC | 参数是否有效，daemon 是否可达 | Mod 已执行 |
| 控制请求 | 是否认证、受理、路由、完成返回 | 游戏动作达到用户目的 |
| 游戏执行 | 游戏真实回调/命令执行提供了什么状态、结果与反馈 | 任意机制已按用户设想工作 |
| 目的与读回 | 调用者检查到什么状态 | 产品知道完整研究结论 |

语法错误和 command source 的游戏反馈必须忠实保留。结果整数 0 可能是合法结果，空输出可能是条件不成立或无反馈；不能统一当失败。无法判定的执行范围必须有 unknown/partial 表达。

## 候选响应结构

```json
{
  "schema": "PROPOSED",
  "request_id": "opaque-id",
  "source": {"instance": "opaque-instance", "run": "opaque-run", "vantage": "server"},
  "request_status": "completed",
  "execution": {"status": "unknown", "result": null, "feedback": []},
  "error": null,
  "limits": {"feedback_truncated": false}
}
```

这是帮助讨论层次的示例，不可直接作为生产 fixture。实际游戏 API 能可靠观察哪些 execution 字段，必须先审源码和真实调用，再固定 schema。

CLI 退出码方案单独决策：参数、不可达、协议/授权、目标不支持、游戏失败、未知和取消是否分别映射，必须和 JSON 一致。即使兼容策略允许受理成功退出 0，也要明确它不证明游戏动作成功。

## 写请求状态机

建议：new → accepted → executing → completed / failed；客户端等待超时属于观察状态，不覆盖源端执行状态。连接断开且无法确认执行时返回结果未知，并保留请求查询入口。

稳定 request ID 的作用域至少包含认证调用者和源实例/run。同 ID 不同载荷拒绝；去重和查询保留窗口机器可发现。窗口失效或 run 更换返回不可恢复/未知，不能把它当安全重试授权。

长快照任务可以有独立 artifact/task ID；必须明确请求返回时只受理、还是已经 ready。取消只有在源端实际确认后才能声明取消成功。

## 最小写协调

先定义冲突，不先实现通用调度系统。候选：普通写按游戏线程排序；需要一致视图的拍摄与相关写互斥；只读在满足一致性约束时并发。具体资源粒度和是否等待由场景验证。

租约不是游戏状态本身。失去连接、到期或释放租约不能隐式解冻；拍摄内部协调的恢复应基于进入时状态和实际执行步骤。所有失败路径提供事实性后置状态。

## 必测结果矩阵

成功非零、成功零、语法失败、权限失败、无目标、execute 条件不成立、异步反馈部分、反馈窗口耗尽、断线前未受理、已受理后断线、结果丢失、重复请求、ID 复用改载荷、重启/账本过期。
